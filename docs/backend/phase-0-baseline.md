## Existing payment flow

### Sample checkout

1. Zustand persists the cart in browser `localStorage` under `garmops-sample-cart`.
2. `src/app/checkout/page.tsx` creates a transaction ID in the browser and sends item IDs, sizes, and quantities to `POST /api/payu/hash`.
3. The route validates canonical products/sizes/quantity bounds, recalculates subtotal and shipping, signs the verified amount, and returns PayU form fields (or a local mock).
4. The browser writes contact, shipping, item summary, amount, and transaction ID to `mf_pending_order`, then posts directly to PayU.

The server-side price recalculation is a useful invariant. The missing durable order/payment attempt means browser clearing or device switching can still sever the order context.

### Configurator reservation

1. In-progress builds use `mf_configurator_build:{configId}` in `localStorage`.
2. Configurator carts/procurement data use `mf_configurator_cart:{cartId}` plus active-cart keys in `localStorage`.
3. Artwork, neck-label, and purchase-order blobs use IndexedDB database `mf-configurator-uploads`; drafts store file keys and reconstruct object URLs.
4. `src/components/configurator/cart/ConfirmationStep.tsx` creates the PayU transaction ID in the browser and requests the server-fixed ₹499 reservation hash.
5. The browser serialises the order summary and IndexedDB purchase-order reference to `mf_pending_order`, then posts to PayU.

The existing configurator state, previews, autosave, and upload recovery are preserved. They remain a guest-draft layer until the cloud import phases.

### PayU callback and confirmation

- `src/app/api/payu/callback/route.ts` validates the signed handoff and PayU reverse hash, then stores a short-lived HttpOnly result cookie.
- There is no durable payment-attempt/event row, webhook route, Verify Payment API call, atomic finalisation, or reconciliation job.
- Success and failure pages validate the cookie but client components reconstruct the order from `mf_pending_order`.
- `src/app/api/send-confirmation/route.ts` requires the signed result cookie for payment emails, but still receives browser-restored order details and uses a per-instance in-memory rate limiter.

Therefore, payment success can outlive the only available order details. Durable checkout must be introduced behind flags before the legacy flow is removed.

## Existing routing and security

`src/proxy.ts` is the sole Next.js 16 proxy and performs agent-readable Markdown rewrites/content headers. Phase 4 must compose Supabase session refresh into it without adding `middleware.ts`. The current `next.config.ts` security headers and exact PayU/Formspree/Resend origins remain unchanged in Phase 0.

The installed Next.js 16 documentation confirms:

- only one `proxy.ts` is supported and it is unsuitable as the final authorisation boundary;
- route handlers are uncached by default;
- `NEXT_PUBLIC_*` values are inlined into client bundles at build time, while server variables remain server-side.
